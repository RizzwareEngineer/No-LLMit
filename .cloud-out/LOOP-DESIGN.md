# Revised loop design

1. Objective: one scripted journey at applied 4x CPU and network: load, 30 s watching, swipe through Stats, the drawer, a stream update while a reason types. Gate each step on time to real content, long tasks and dropped frames; gate total main-thread time and bytes. Swipe to Stats within 300 ms. Lighthouse is reported, not gated.
2. Fixture: the real engine on frozen inputs (hand-log snapshot, seeded deck and mock model), two data sizes, edge states (typing at load, closed, at cap, reconnect, long names, big bets). Unserved calls fail the run. Accept it when base verdicts match live.
3. Gates: one script with a JSON verdict, run fresh in the cloud, never by the builder. It restores checks, fixture and settings from the base by hash; diffs that touch them fail. A known-bad corpus (past bug commits, a planted LCP trick, a vacuous check) must fail first and after any gate change. Freeze the red list; judge red checks by measured detail.
4. Statistics: an A/A run sets the noise. Each idea names one mechanism metric and a predicted gain; other metrics get margins. Add runs until the interval clears or rules out the minimum gain, else "inconclusive". Confirm winners in a fresh session; a second instrument must agree on the sign.
5. Unchanged means: same boxes and text in a frozen settled mode; filmstrips with each region filled no later than on the base, no new empty state or pop-in; same text, accessibility tree and controls.
6. Lanes: the speed lane owns the baseline and lands only invisible changes. Each visible change is a query-flag draft on the latest baseline, gated on speed non-inferiority, invariants and an unchanged desktop. The owner picks on a cloud preview; a yes flips the default. Open picks block their area. The mobile lane follows, from his asks.
7. Levers: the stream's opening payload, hydrating only the shown layout, a server-rendered first frame as a draft. A new lever needs a traced cost.
8. Integration: one builder per disjoint file group. The cloud stacks winners by measured gain, regates each addition, drops failures. One squashed commit per idea, a tag per baseline. Code review on each diff and the stack, one repair pass.
9. State: one durable file in the private internal-docs folder (base SHA, runs, idea status and interval, red list). A dead run is "not evaluated".
10. Stop at the time or budget limit, or when no idea left can reach the minimum gain. Then one large interleaved set, original base against final stack, plus Vercel Preview and WebKit passes. One digest: journey numbers, score with interval, films, drafts to pick. PRs to main only on his yes.

H2 Gates: gate script (JSON verdict, hash pin, path rule, user-agent rule, second instrument), known-bad corpus, frozen red list; fix stats-while-typing, which passes on a bare #race-panel.
H3 Journey: journey script, element timing, filmstrips, information inventory.
L1 Stream opening payload (engine stream code, lib/api.ts); metric: bytes before first data.
L2 Hydrate only the shown layout (page.tsx); metric: hydration CPU over traced runs.
L3 Server-rendered first frame behind ?ssr=1 with stream resume; metric: real-data paint time. A draft, rebased only after his yes.
Builders state metric and predicted gain first; check edits get their own commit.
Local, reading only: create the state file; review each pushed diff (reviewer plus skeptic); send him one message: open picks (seat, shape, About, ?ssr) with a recommendation each, plus two asks (Preview API URL, CI workflow for WebKit). No builds or browsers on the Mac.

## Kept issues

### Deferral is free: the gates see one cold load and settled frames, not the viewer's journey (blocker, during round 1)
Merges 'Moving cost later is free', 'The loop measures the load and the settled end' and 'The target is a lab number'. Lighthouse scores one cold load with no input, and G4 compares settled frames. Work moved to the first swipe, the drawer or later updates leaves the score and lands on the viewer, so a deferral is always the cheapest change that passes. This already happened. The stats deferral (0a33396) moved about 500 ms of 4x-CPU work to the first swipe and left the stats empty while a reason typed. Only code review caught it. The owner's own second target, Stats visible within 300 ms of a swipe on a slow phone, has no gate. An agent can also gain points by changing which element counts as LCP without painting data sooner.

Change: Make the objective one scripted journey under one applied throttling model (4x CPU, phone network): load, 30 s of watching, a swipe through each Stats window, the drawer, and a stream update while a reason types. Gate each step on time to real content (element timing on data, not on an empty box), long tasks and dropped frames. Gate the whole journey on main-thread time and bytes. A deferral passes only if total work does not grow and every step stays in budget, with swipe-to-Stats within 300 ms. Reject a change that moves the LCP element unless real-data paint time improves. Report the Lighthouse score but never decide on it.

### The A/B is underpowered and runs many tests, and the stack locks in its errors (blocker, during round 1)
Merges 'The A/B cannot see the gains that are left', 'Guards cannot prove not worse', 'Many tests per round inflate wins' and 'The A/B gates judge noise'. The same code scored 77-85 between sets, but single changes have moved only 0-3 points. Perf step 2 went from 79 to 78 on 3 runs a side and was dropped without anyone learning whether it removed its target work. So 9+9 runs mostly return chance. 'No metric is worse' is undefined. As a point estimate it vetoes about half the time for each metric; as an interval it vetoes almost nothing. Several ideas times many metrics per round let noise pass with an inflated gain. Each stack becomes the base, so false accepts add up, and each accepted diff has brought 13-32 real defects. 'Two rounds with no gain' fires on noise, and the ledger records real gains as tried and failed.

Change: Open each measuring session with an A/A run (base against base), and void the session if A/A passes. Before measuring, each idea declares one mechanism metric and a predicted gain: exact bytes, or the traced CPU time of its target task over about 30 interleaved, paired runs. Every other metric gets a stated margin ('not worse by more than X') and a non-inferiority test. Add runs until the interval clears a minimum worthwhile gain or rules it out. The ledger stores each effect with its interval, or 'inconclusive'. Confirm each winner in a fresh session before it joins the stack. Pin Chrome and Lighthouse, use a fresh browser per run and log the benchmark index. Only one large interleaved run of original base against final stack decides 'target met' and feeds the digest. Stop when no remaining idea can reach the minimum gain.

### One gate set and one baseline serve two loops with opposite aims (blocker, before the first round)
Merges 'One speed rule serves two loops', 'The gates are not scoped to the mobile loop', 'Visible changes stack into the baseline', 'Both loops share one baseline' and part of 'The mobile loop has no problem to solve'. G3's superiority test rejects every UX change that leaves speed the same. G2 pins today's phone design (28x40 hole cards, nine logos, Stats order), which the mobile loop exists to change. G2's red-on-base rule also leaves the phone seat checks unguarded. The mobile loop edits Player, PokerTable and TableFelt, which the locked desktop table shares, and no gate keeps the desktop unchanged. Visible changes stack before the owner sees them, so one 'no' cancels everything built on top. The loop can also settle his open picks (seat layout, table shape, About) without him. His taste rules are limits, so they cannot rank 'better'.

Change: The speed lane owns the baseline and lands only invisible changes. Every visible change is a query-flag draft (like ?seat=tucked) on the latest speed baseline, never on another unapproved draft. This includes a speed lever that changes the load sequence. A draft must pass speed non-inferiority, the invariants and a check that the desktop and every other non-phone state are unchanged. Keep a speed budget per round so the margins cannot add up. Split checks into invariants (frozen) and phone-design specs. A draft may update a spec check with his yes, together with its visual change. He picks drafts on a cloud-hosted preview, not a build on his Mac. A yes flips the default, and the change joins the next baseline. Areas with an open pick stay out of bounds. Send him one message with the open picks and a recommendation for each. The mobile lane starts after the speed lane, as he asked, from his written asks and open findings (contrast, tap targets).

### Pixel identity and stills are the wrong tests for 'nothing people see changed' (blocker, during round 1)
Merges 'Pixel-identical screenshots are the wrong test', 'Showing less wins every gate', the gate part of 'Stills cannot show motion or touch' and the filmstrip part of the load-and-settled-end issue. The page's pixels depend on time (typed reason, shot clock, countdown, Trends replay). So pixel identity is either flaky or loosened until it misses the known failure, and it forbids painting real content sooner. Settled frames miss late regions, pop-in and new empty states. Viewport shots miss removed content: off-screen rows, server HTML, the accessibility tree. About and the stats already left the home page's HTML, and no gate noticed. Most of his repeated feedback is about motion and touch, which stills cannot show: the peel, the tile flash he reported three times while DOM checks passed, the swipe kick-out.

Change: For the speed lane, replace pixel identity with three tests. (a) Settled state in a frozen mode (pinned clock, stream paused at a fixed event, animations done): layout boxes and text must be identical, and pixels within an A/A noise floor. (b) Filmstrips of the journey: each region fills no later than on the base, no new empty state shows while the data is in hand, and no new shift or pop-in appears. The motion rules also run as checks: nothing slides in on load, no frame is blank, nothing moves behind a modal. (c) An inventory for each state: server HTML text, DOM text, accessibility tree, links and controls, and the gestures needed to reach each. It must not change for a speed change. For a draft, every removal and every move behind a tap is listed for the owner. Send him films, not stills, for anything that moves.

### The gates are unproven, and the builder can grade itself and bend its checks (blocker, during round 1)
Merges 'The checks are the soft spot', 'The builder grades itself', 'The gates are not proven' and the red-list part of 'Guards cannot prove not worse'. Put the stats deferral through the design. G2 passes because no check existed yet, G3 passes because the score rose, and G4 passes because the settled screenshots match. Only code review caught it. Some checks still pass without testing anything. Verified: statsShown in stats-while-typing also returns true when #race-panel merely exists. Verified: 0a33396, 0565f78 and 9d0993c each edited checks.mjs, because a deferred mount changes how a check reaches the page. 'May not edit checks' is an instruction with no enforcement and no legal path. The design does not say where G1-G5 run. With the Mac idle, the natural place is the builder's own run, which then grades itself. Together, 'red on base is pre-existing' and 'rerun alone' make red and load-sensitive checks permanent blind spots.

Change: One gate script returns a JSON verdict and runs outside the builder, in a fresh cloud run (or in CI, on his yes). It restores checks, audit, fixture, Lighthouse flags and runner setup from the base, pinned by hash. A diff that touches them fails by a path rule. The base's results are computed once per round and shared. Check changes get their own lane. A changed check must fail on a planted defect and pass on base. It applies to both arms, and it never merges in the same step as the code that needs it. A phone-spec change needs his yes. Before any verdict, a known-bad corpus must fail. It holds the commits behind past bugs (stats empty while typing, the clock outliving its effect, a failed chunk blanking the stats, the Trends failures at 1,250 hands), a planted LCP trick and a check that tests nothing. Rerun the corpus after any gate or check change. Freeze the red list at the start and show it to him. Judge red and flaky checks by failure rate and measured detail, under the same suite load on both arms. Code review runs on each pushed diff while the gates run, with one repair pass before a reject.

### The fixture re-implements the engine and freezes one moment at one data size (major, during round 1)
Merges 'The fixture is a second engine to build and prove', 'A frozen, local fixture makes staleness and scale invisible', 'One recorded moment stands in for every arrival' and the data part of 'Every gate sees one session'. A replay server must copy nine message types, reconnects, 503 retries and the other endpoints (/api/stats/timeline, /api/usage, /api/waitlist). It does not exist yet and sits on round 1's critical path. Builders cannot fix it, so its bugs become verdicts. A byte recording also cannot measure server-side levers such as the stream's opening payload. One moment fixes one arrival phase and the smallest data size the site will ever send. Five Trends checks broke only at about 1,250 hands. Seat drafts passed with tiny bets but failed with bets of 120 and 1,250. A frozen recording also cannot tell fresh data from a snapshot built into the page.

Change: Run the real engine on frozen inputs: a hand-log snapshot (the kind scripts/dev.sh --seed builds), plus seeds for the deck and the mock model. Verified: engine/game/deck.go seeds its random source from the time, so the deck needs a seed flag. Accept the fixture when the base's suite gives the same verdicts on it as on a live engine, with each difference explained. Keep a small set of fixtures. It covers today's size and one size past the timeline caps. It also covers arrival phases and edge states: a reason typing at load, showdown, closed, at cap, a lineup change, reconnect, the longest names and big bets. Serve every endpoint from the fixture, and fail a run that makes any other call. Run the speed A/B on both sizes and the visual gates on all fixtures. Add a freshness check: build against snapshot A, serve snapshot B and require B on screen. Also gate the time from a stream event to its pixels.

### Lab gains may not reach real phones, and nothing checks that they do (major, during round 1)
Merges 'One lab instrument and a recognisable client', 'The lab is neither the network path nor the phone', the browser and font part of 'Every gate sees one session' and the WebKit and beacon part of the launch-risks issue. The score is Lighthouse's simulation of one cold load in emulated Chrome, served from the VM. Production serves the page from Vercel's edge (HTTP/2, Brotli) and the stream from an engine on another host over TLS. The simulator has no model for a stream that the server times and that never ends. Many viewers come from X on iPhones, where every browser is WebKit with the SF font. No gate runs WebKit, and the VM measures the one-line and 11px rules in a fallback font. Speed and pixels come from different tools with different emulation, so a page can be fast for one tool and complete for the other. The site reports no web vitals, so nobody will learn whether the gains reach viewers.

Change: Accept a speed gain only when a second instrument agrees on its sign. Use perf-trace.mjs with applied 4x throttling, a normal phone user agent and no automation flags, on the same build as the pixel and inventory gates. G1 fails any app diff that reads the user agent, navigator.webdriver, harness globals or device hints to change what loads. Measure the base and each stack on a Vercel Preview, with the engine over https. Trust the lab for a kind of lever only while its deltas predict the preview's deltas. Run the phone flows and the text-fit checks in WebKit with the system font, on a macOS runner. Add a web-vitals beacon so field p75 numbers can confirm the gains after launch. The digest says which number '90' refers to.

### The gap is already diagnosed, and its biggest lever is visible (blocker, before the first round)
Merges 'The speed loop's nothing-visible rule shuts out the one lever that reaches 90' and 'A general search loop for a gap that is already diagnosed'. Three of the five metrics already score full marks: FCP 0.8 s, SI 1.5 s, CLS 0.005. All lost points come from LCP (about 3.9 s) and TBT (about 400 ms). About 90% of LCP is render delay. Verified in PERF-GATE.md: the LCP element is a P&L model name that paints only after the JS downloads and React hydrates, and the stream already opens from the HTML. On Lighthouse's curves, LCP 3.9 s scores 0.53 and TBT 400 ms scores 0.68, for a total of 0.79. With TBT at 0, the total is still only 0.88. To reach 90 with invisible work alone, TBT must fall to about 250 ms and LCP must lose about 0.9 s. The reports already name what is left. Both layouts' trees are prerendered and hydrated, then one is dropped. The stream opens with about 188 KB uncompressed, including the all-time stats body that a phone does not mount. The first frame waits on the client. Three analysts per round would find these again, at about 9% of the week per round. Meanwhile, the pixel-identical first paint, skeleton-matches and the small-diff rule forbid the one change that removes the wait: real content in the first HTML.

Change: Drop the open search and the analysts. Run one targeted job per named lever. Judge each job first on its mechanism metric, then on the journey, and last on the Lighthouse A/B. (1) The stream's opening payload: move the stats body out of the first message or compress it. Measure bytes before the first data against the real engine. (2) Hydrate only the shown layout. Measure hydration CPU in traces. (3) Server-render the first frame from the latest snapshot, and resume the stream from that frame. Build it as a ?ssr draft, and take it to the owner with its measured gain. It changes the load sequence, and skeleton-matches must change with his yes. Add a lever only when a trace shows a new cost.

### The loop's shape fits neither the clock nor parallel merges (major, before the first round)
Merges 'A round takes about 6 h and 15% of the week' and 'Parallel ideas collide in the same files'. One round is serial: measure, diagnose, three builders of 2.5-3 h, review, then a stack gate of 2.5 h. That is about 6 h and five cloud runs, about 15% of the week. Round 1's measure run cannot finish before 06:20. 'Two rounds with no gain' costs about 12 h and 30% of the week before it fires. Recent perf commits cluster in page.tsx, StatsScreens.tsx, StatsSections.tsx and lib/api.ts, so the top ideas collide and their gains do not add up. Past hand-merges dropped a prop that the phone popup needed and weakened three checks. Runs have died or lost their reports (usage cap, classifier outage). A reboot wiped the scratchpad, and the main session's context reached 88%.

Change: Start one wide round now on the latest base and the saved perf traces, with no fresh measure run. Give each builder a disjoint group of files. Ideas that share a file go to one builder, in order. Builders work now and are gated when the harness lands. Integrate in the cloud in order of measured gain. Rebase each idea onto the growing stack, rerun the gate script after each addition, and drop an idea that fails. Then review the final stack diff, merge resolutions included. Keep one squashed commit per idea and a tag per baseline, so a bad idea is one revert. The stack's gate run is the next round's measurement. Keep the loop state in one durable file in the private internal-docs folder, and re-read it every tick. The state is the base SHA, the run IDs, each idea's status, reason and interval, and the red list. A dead run is 'not evaluated', never 'rejected'. Cloud runs write small summaries, so the Mac never pulls raw traces.

### The vision judges answer the owner's question with no ground truth (major, later)
Merges 'Judges are asked the owner's question', the judge part of 'Stills cannot show motion or touch' and the judge-panel part of 'The mobile loop has no problem to solve'. The judges' rubric and their calibration set come from the same feedback, so agreement only grades their own source. That feedback is mostly complaints with a single label. 8 of 10 on about ten items fits anything from a coin flip to near-perfect. Three judges from one model share blind spots, and stills cannot show motion. Where his rules conflict on a narrow phone (one line, 11px floor, whole names at 360 px), the judges would decide his taste for him. Meanwhile, nobody covers the breadth he cannot check on a phone: every state, size, zoom level and fixture.

Change: Judges stop deciding 'better'. They hunt regressions across the full state matrix and get frame strips for motion. Score them on seeded defects: 10px text, a wrapped line, an empty band, a clipped figure, a bubble over cards, a removed feature he liked. That gives a labelled score at no cost to him. He judges 'better' with A/B picks on the real page. Keep his picks as a held-out set, and let the judges pre-filter for taste only once they agree with enough of his picks. Rule conflicts go to him.
